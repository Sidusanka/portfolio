Cloud efficiency

FinOps cost optimization

Evaluated Intel and AMD VM options for Azure Kubernetes Service, supported SKU migrations, and decommissioned unused Azure resources. The comparison identified estimated per-node compute savings of 50–54%.

My role
VM right-sizing, migration planning, and resource decommissioning
Technologies
Azure Kubernetes Service · Azure Virtual Machines · Kubernetes · FinOps

Context

I contributed to an enterprise Azure cost optimization initiative covering Azure Kubernetes Service (AKS) clusters, virtual machines, and supporting resources in East US, Australia East, and West Europe. The work focused on right-sizing compute and retiring resources that were no longer needed.

Problem statement

One AKS node pool used Standard_D16d_v5, an Intel Xeon VM with 16 vCPUs, 64 GiB of memory, and 600 GiB of temporary storage. Moving to a smaller SKU could lower compute costs. The target VM still needed enough capacity for existing workloads, support for the node pool’s ephemeral OS disk, and availability within the region and subscription quota. Replacing nodes also had to account for Kubernetes scheduling and disruption limits.

My contribution

I reviewed AKS node pools for right-sizing opportunities, compared Intel and AMD SKUs, and assessed regional availability, compute quotas, and OS disk compatibility. I investigated workload disruption constraints, documented the findings, and supported VM SKU migration and unused-resource decommissioning.

Technical approach and implementation

  1. Assess infrastructure and cost. I reviewed existing AKS node-pool configurations, allocated CPU and memory, and estimated compute costs to identify candidates for right-sizing.
  2. Compare smaller Intel and AMD SKUs. I compared Standard_D16d_v5 with Standard_D8ads_v5 (AMD EPYC) and Standard_D8d_v5 (Intel Xeon). Both candidates halved per-node vCPU and memory allocation to 8 vCPUs and 32 GiB. Right-sizing accounted for most of the estimated savings, with the AMD pricing providing a further reduction.
  3. Check regional availability and storage compatibility. Regional SKU availability and subscription compute quotas limited some AMD options, so I evaluated the smaller Intel SKU as a fallback. I also checked whether each candidate had sufficient supported local storage for the node pool’s ephemeral OS disk.
  4. Review workload scheduling and node drains. Smaller nodes leave less allocatable CPU and memory for pods, so I reviewed workload requests, limits, and scheduling requirements. I also checked PodDisruptionBudgets because restrictive budgets can block voluntary pod evictions during a drain.
  5. Decommission unused Azure resources. I helped identify resources that were no longer required and retire them through the existing operational processes.

Technical challenges and lessons learned

The feasible SKU depended on region, availability zone, and subscription quota. A smaller VM could meet CPU and memory needs while offering too little supported local storage for the ephemeral OS disk. Even with a compatible SKU, node replacement depended on whether workloads could be evicted and rescheduled safely.

Project outcomes

The evaluation identified a potential 50–54% reduction in per-node VM compute costs and documented the constraints that determined which SKUs were viable. I also contributed to Azure VM SKU migration and unused-resource decommissioning.

Engineering takeaway

I compare the effect of reducing allocated CPU and memory separately from the price difference between processor families. Before recommending a SKU, I check that it meets workload capacity, storage, regional availability, and operational requirements.
