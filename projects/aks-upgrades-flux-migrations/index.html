Platform engineering

AKS upgrades and Flux CD migrations

Worked with the platform team over several months to upgrade AKS from Kubernetes 1.32 to 1.35 in three stages and verify Flux CD reconciliation.

My role
Upgrade planning and execution
Technologies
Azure Kubernetes Service · Flux CD · GitOps · HCP Terraform · GitHub Actions

Context

This work was part of my cloud platform role, upgrading the Azure Kubernetes Service (AKS) clusters that ran our containerized workloads. Over several months, I worked with the platform team to plan and carry out three successive upgrades from 1.32 → 1.33 → 1.34 → 1.35. We scheduled each stage as Azure made the target version available.

Problem

Each upgrade had to account for three risks. A workload or controller could depend on an API removed in the target release. A restrictive Pod Disruption Budget (PDB) could block node drains and extend the maintenance window. Flux CD could have reconciliation failures even after Azure reported that the infrastructure upgrade had completed. We needed to check Kubernetes compatibility, workload health, and GitOps reconciliation at each stage.

Approach

  1. Review each target release. I read the Azure AKS and upstream Kubernetes documentation for each version, focusing on breaking changes and APIs that were deprecated or removed. I checked where those changes could affect workload manifests, controllers, and integrations before we scheduled the upgrade.
  2. Plan the maintenance with workload owners. I checked cluster health, node pool versions, and PDBs before each window. We reviewed potential drain blockers with the teams that owned the workloads, estimated the window using node count and time for verification, and notified the affected teams in advance.
  3. Apply reviewed infrastructure changes and verify the rollout. I prepared the version change for peer review and applied the approved change through HCP Terraform. I monitored the rollout in the Azure portal and used OpenLens to check that nodes reached the expected version and to look for failing pods or service issues.
  4. Verify Flux CD before and after its upgrade. I checked the installed version, controller pods, and Kustomization status before running the Flux upgrade workflow in GitHub Actions. Afterward, I checked the controller version and Kustomization readiness to confirm that Flux was applying the desired state from Git. I also checked node pool patch versions because a Flux maintenance plan could include an AKS node pool patch upgrade and require a longer window.

Outcome

We completed all three upgrade stages and reached Kubernetes 1.35. Each stage had its own compatibility review, maintenance window, and post-upgrade checks. For the Flux CD work, Kustomization status gave us a direct way to verify that GitOps reconciliation was working after the upgrade.

Engineering takeaway

I treat an AKS upgrade as complete once the nodes are running the expected version, workloads are healthy, and Flux is reconciling the desired state from Git. Planning one minor version at a time gave the team a chance to address compatibility risks and verify those conditions before moving to the next release.
